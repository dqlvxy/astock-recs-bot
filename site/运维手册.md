## 二、三处校正

### 校正 1 · 重新发布目录（原手册第四节）

原手册写：

```
cd F:/WorkBuddy/2026-10-08-17-25-21
npx wrangler pages deploy pagesite --project-name=astock-board --branch=main
```

**问题**：这个路径下的 `pagesite/index.html` 可能是**过期副本**。
实测该目录里存在过两个旧版本：
- `725000` 字节 · md5 `0963cfde480eac045466b23074ac42db`
- `725481` 字节 · md5 `943a7f7953b6fcfaee2a29b8c482dff0`

都与线上当前版本 `68f5fb64…`（`726098` 字节）不一致。

**用旧文件部署会把「同源优先」bug 重新带上去**（见坑 4）。

**正确做法**：

```bash
# ① 先确认 pagesite 目录里 index.html 的 md5
certutil -hashfile pagesite\index.html MD5
# 或 PowerShell：
# Get-FileHash pagesite\index.html -Algorithm MD5

# ② md5 必须是 68f5fb6474460bb183fa2b4e7f852a10 才是线上最新版
#    不是的话，从线上重新下载覆盖：
curl -o pagesite\index.html "https://astock-board-9t0.pages.dev/"

# ③ 确认目录里没有三个死文件（有就删）
del pagesite\today.json pagesite\watch.json pagesite\recs.json

# ④ 部署
set CLOUDFLARE_ACCOUNT_ID=bebe9230db6ff26dff3368b43387d521
set CLOUDFLARE_API_TOKEN=<你的 Cloudflare API 令牌>
npx wrangler pages deploy pagesite --project-name=astock-board --branch=main
```

> 更稳的办法：以后固定用一个专门的发布目录（如 `F:/WorkBuddy/pagesite`），
> 只放 `index.html`，避免和日期命名的临时目录混淆。

### 校正 2 · 幂等发布的判断（原手册第四节的补充）

原手册写：

> 输出 "Uploaded 0 files" 表示内容与线上一致，属幂等发布，不是失败

**补充**：wrangler 4.x 的措辞是 **`Success! Uploaded N files (M already uploaded)`**。
沙箱实测幂等时输出：

```
✨ Success! Uploaded 1 files (15 already uploaded)
```

只要看到 **`✨ Deployment complete!`** 就是成功，不必纠结上传数量。
另外每次部署会分配一个**新的预览域**（形如 `https://61ff242e.astock-board-9t0.pages.dev`），
主域 `astock-board-9t0.pages.dev` 始终指向最新生产版本。

### 校正 3 · 坑 3 的强化（原手册第三节）

原手册写：

> 【坑3】Cloudflare Pages 有 SPA 回退：访问不存在的静态文件返回 200 + text/html

**实测确认**（`2026-10-09 02:28`）：

```bash
curl -sI "https://astock-board-9t0.pages.dev/__不存在__.json"
# → HTTP/2 200
# → content-type: text/html; charset=utf-8
```

**这比 404 危险，必须按下面方式判断**：

```bash
# ✗ 错误：只看状态码
curl -s -o /dev/null -w "%{http_code}" ".../today.json"   # 永远 200

# ✓ 正确：同时验内容类型
curl -s -o /dev/null -w "%{http_code} %{content_type}" ".../today.json"
# 200 text/html  → 文件不存在（被 SPA 回退成 index.html）
# 200 application/json → 文件真实存在
```

**推荐直接验内容**：

```bash
curl -s "https://astock-board-9t0.pages.dev/today.json" | head -c 20
# 出现 <!DOCTYPE html> → 不存在
# 出现 {"ok":true,...  → 存在
```

## 四、九个坑（原手册第三节，全部实测证实，保留）

- **坑 1** · `github.com` 本机间歇阻断，`api.github.com` 稳定。
  > **补充**：沙箱环境两者都通（实测 `github.com` 200 / `api.github.com` 200），
  > 沙箱可以直接走 API 推送。电脑端才需要 `--host-resolver-rules` 指定 IP。
- **坑 2** · GitHub Actions 的 runner 用 POSIX `sh`，**不支持中文变量名** → 一律 ASCII。
  > ⚠ **曾修漏，2026-10-12 复发**：此前只把「刷新 CDN 缓存」步骤改成 ASCII，
  > 「提交快照文件回仓库」步骤里的 `提交了` 一直残留，导致
  > **10-09、10-12 两次运行 exit 127 失败** —— 选股与快照都生成成功，
  > 却卡在提交，数据进不了仓库，看板走势图长期停在旧数据。
  > 现已全量改为 `HAS_FILE`，并加了 `git pull --rebase` 防并发推送被拒。
  > **判断依据**：日志里出现 `xxx=0: command not found` + `exit code 127`。
  > **排查命令**：`gh run list --limit 5` 看结论，`gh run view <id> --log-failed` 看步骤。
- **坑 3** · Pages 有 SPA 回退，不存在文件返回 `200 + text/html`，**必须同时看 content-type**。
  （强化说明见上方「校正 3」）
- **坑 4** · 看板数据源**只走 jsDelivr CDN**，不要再加「同源优先」。
  同源副本不会被 Actions 更新，会**把数据永久冻死**。
- **坑 5** · jsDelivr **分支地址（@main）会被边缘节点长期缓存**，且 purge 未必生效。
  对策：前端走「commit 哈希地址 + 分支地址」**双路并发**，比较文件里的
  `updated` / `gen_time` 取较新的一份（见 `取双地址()` / `拉一份()`）。
  单用哈希会被写死的值锁住，单用分支会被缓存钉住，两者互补才稳。
- **坑 6** · 图表读 `getData("/api/recs")` 时**优先返回 EMBED 内嵌快照**，
  内嵌是随页面编译进 HTML 的静态数据，日期永远停在打包那一刻。
  > 后果：即使云端已生成新交易日，「近 5 日表现走势」依旧画旧记录，
  > 表现为「图永远不变化」。
  > 对策：`renderRecChart()` 改为 **云端 `window.__后端recs__` 优先**、
  > 内嵌仅作兜底，按日期归一去重后合并，再取最近 5 个交易日。
- **坑 7** · wrangler 部署 Pages Functions 有目录坑：**在父目录用子目录名部署
  （`npx wrangler pages deploy astock-site`）不会编译、不会上传 Functions**，
  日志里没有 `✨ Compiled Worker successfully` / `✨ Uploading Functions bundle`，
  部署“成功”但 `/api/*` 全被 SPA 回退成首页 HTML（`200 + text/html`）。
  > 2026-10-14 实测：资金流模块因此走了一整天涨停封单兜底，显示"资金流接口未接通"。
  > 正确做法：**cd 进发布目录，用 `.` 部署**：
  > ```bash
  > cd astock-site
  > npx wrangler pages deploy . --project-name=astock-board --branch=main
  > ```
  > 判断依据：日志必须同时出现 `Compiled Worker successfully` 与 `Uploading Functions bundle`；
  > 验收命令：`curl -s <域名>/api/fund` 应返回 `application/json`，不是 HTML。
- **坑 8** · 资金流模块「中国电信 PoP 故障」：同一个 `/api/fund`，沙箱 3/3 正常、
  手机（中国电信）却取不到 —— 不同 Cloudflare PoP 到上游（新浪 JSONP）的可达性不同，
  边缘代理在故障 PoP 上超时/失败，模块只能回退涨停封单。
  > 2026-10-15 加固为**三级容灾**，任何一级挂掉都不再出现"资金流接口未接通"：
  > 1. **函数侧**（`functions/api/fund.js`）：所有上游 fetch 加 6 秒超时；
  >    新浪失败换 cache-bust 参数重试 1 次；`caches.default` 边缘缓存成功响应 2 分钟；
  >    上游全失败时回退**过期缓存**并标 `stale`（宁可给 2 分钟前的真实数据）；
  >    `onRequest` 整体 try/catch —— **永远返回 JSON**，杜绝 fail_open 回退 HTML。
  > 2. **前端侧**（`fetchSectorFund`）：代理失败立刻重试一次（换 `?t=…-2`），
  >    再不行走 **today.json 当日快照**（`sector_fund`，Actions 侧拉的新浪数据，
  >    与代理同为口径，标注"云端快照 HH:MM"），最后才回落涨停封单。
  > 3. **数据侧**（`today.js`）：main() 第 [8/8] 步拉新浪资金流写入 `sector_fund`，
  >    经 Actions 每日提交进仓库，前端 `应用全模块快照` 白名单已含该字段。
  > 验收：`curl -s <域名>/api/fund` 看 `content-type` 与 `rows` 行数；
  > 线上模拟 PoP 故障可临时覆盖 `window.fetch` 拒绝 `/api/fund` 再调
  > `fetchSectorFund()`，应见"新浪财经 · 云端快照 HH:MM"。

- **坑 9** · 2026-10-15 三连击（部署目录 / CDN 陈旧 / 成本口径），三个都实测复现：
  **9a · wrangler 部署的工作目录陷阱（Functions 整包丢失）**
  在 `/workspace` 下执行 `npx wrangler pages deploy . --project-name=astock-board`
  会上传 `/workspace` 全树 219 个文件、**完全不编译 Functions**，
  把线上降级成"无函数版"——`/api/fund`、`/api/recs` 全部 404。
  根因：Bash 工具的工作目录**不跨调用持久化**，`cd X && cmd` 只对当条命令有效。
  > 铁律：部署命令必须写成 `cd /workspace/astock-site && CLOUDFLARE_ACCOUNT_ID=… CLOUDFLARE_API_TOKEN=… npx wrangler pages deploy . --project-name=astock-board --branch=main` 一条链；
  > 且日志必须含 `Compiled Worker successfully` + `Uploading Functions bundle`，缺一即未部署函数。
  > 自检.sh [3b] 节已加 `/api/recs` 探针，函数丢失立刻暴露。

  **9b · jsDelivr `@main` 边缘节点散发"被覆盖前的旧版本"**
  17:54 手动补跑把 10-15 期从 15:12 定时版覆盖为金域医学版后，
  `@main/recs.json` 在部分边缘仍返回定时版（京能热力版）——
  看板「今日持股」差点显示用户并未实购的股票。
  验真身只能用 `https://raw.githubusercontent.com/<repo>/main/recs.json`（无 CDN 缓存）。
  > 修复（双保险）：① 新增 `functions/api/recs.js` 同源边缘代理，服务端直拉 raw（永远新鲜）、
  > jsDelivr 仅作备用、30 秒边缘缓存、全失败回退过期缓存标 `stale`、永返 JSON；
  > 前端「拉后端存档」改为同源 `/api/recs` 优先，失败回落原「哈希+分支」双路。
  > ② `curl https://purge.jsdelivr.net/gh/dqlvxy/astock-recs-bot@main/recs.json` 手工刷新分支缓存。
  > 前端旧「哈希+分支」双路救不了此坑：哈希地址静态写死，不会每日更新。

  **9c · 浮盈成本优先级写反（策略价冒充实付成本）**
  `renderTodayHold` 把 `x.买入价/buy_price`（引擎约 14:30 算出的理论买点）
  排在 14:50 建仓快照之前，导致浮盈显示 -0.35%（策略价成本），
  而按 14:50 实价口径真实浮盈是 +0.19%——方向都反了。
  > 铁律：成本链 = **14:50 建仓快照（真实成交口径）→ 策略买入价（兜底）→ 现价**。

  **9d · 荐股定稿（14:30）与建仓成本（14:50）必须拆成两个时点（同日二次修正）**
  老板流程固定为：**14:30 荐股定稿 → 14:50 尾盘买入 → 次日涨了卖**。
  曾把 `过1450` 六处判定统一成 14:50，**方向错了**——那会把「荐股定稿 / 上报 / 认当天」
  一并推迟到 14:50，14:30–14:50 期间看不到今日荐股。正确做法是拆成两个函数：

  | 函数 | 时刻 | 用于 |
  |---|---|---|
  | `过1430()` | 14:30 | 荐股定稿、上报/补报荐股、守护拉云端、缓存定稿判定、「认当天」 |
  | `过1450()` | 14:50 | 建仓快照写入、建仓日（浮盈起算） |

  看板内**只保留一处定义**（3472 / 3478 行），另两处同名定义已删除，彻底消除函数遮蔽。
  前端另加「预演版」标注：云端定稿未到时明确提示「当前为本地预演版，仅供参考 · 下拉刷新取定稿」。

  **9e · 云端定稿不准时 + 可被覆盖（同日双版本根因，已修）**
  ① **不准时**：`daily.yml` cron 原 `30 6 * * 1-5`（14:30 CST 触发），GitHub 免费版实测
  延迟 5~20 分钟，极端一次 42 分钟（15:12 才出）→ 用户 14:50 买入时云端还没有今日荐股，
  只能看本地引擎预演 → 两版不一致。
  > 已改 cron 为 `15 6 * * 1-5`（14:15 CST 触发），留 15 分钟延迟缓冲，保证 14:50 前定稿落地。

  ② **可被覆盖**：`generate.js` 里 `filter(date !== 新期.date)` 会让同日重跑覆盖当日定稿
  （17:54 手动补跑就是这样把 15:12 定稿换成了另一版）。
  > 2026-11-09：手动触发入口与 `FORCE` 环境变量**已整体删除**，冻结规则无任何绕过路径。
  > 经 stub 引擎三场景实测：有定稿→跳过、有定稿+FORCE→强制覆盖、无定稿→正常生成。

  ③ **沙箱推不动 git**：`github.com:443` 时通时断（`git fetch` 常超时失败），
  但 `api.github.com` 稳定可用。
  > 改仓库文件走 **Contents API**（`PUT /repos/{owner}/{repo}/contents/{path}`，
  > 带 PAT、base64 内容 + 旧 sha），比 `git push` 稳得多；提交后用 API / raw 回读验证。

  **9f · 「近 5 日表现走势」横轴口径错位（用户："今天的涨幅应该是负的啊"）**
  `renderRecChart` 的横轴原用**荐股日**，未结算期（今日）用 picks 自带的
  `pct_chg`（荐股日当日涨幅）占位 → 图上最后一根显示 **+2.4%**，
  而那是 14:50 买入**之前**已经涨掉的幅度，不是收益；用户今天的真实收益

  > 修正：横轴归位到**结算日**（= 收益实际发生日，T+1），未结算期不占柱、不计入统计；
  > 说明文字改为「横轴为该期结算日……买入前的涨幅不计入成绩；今日荐股待次日结算，见今日持股」。

## 五、架构决策记录：为什么不用同源

这是本轮最重要的一个修复，单独记下来，避免以后有人「优化」回去。

**曾经的实现**：`取全模块快照地址()` 返回 `"today.json"`（同源相对路径），
`拉全模块快照()` 先试同源，404 才回退 jsDelivr。

**为什么错**：
1. 同源 `today.json` 是随看板一起部署到 Pages 的**静态文件**
2. 每日更新由 Actions 推到 **GitHub 仓库**、经 jsDelivr 分发
3. **Actions 更新不到 Cloudflare Pages** → 同源那份永远停在部署那天
4. 它一直返回 `200`（SPA 回退）→ 前端 `r.ok` 为真 → 以为拿到了数据
5. CDN 那份新的**永远轮不到被读** → 数据被冻死

**实测佐证**：同源 `gen_time = 2026-10-09 01:53:19`（手工传的），
CDN `gen_time = 2026-10-08 18:02:39`。看似同源更新，但**明天 Actions 一跑**，
CDN 变成 10-09 新数据、同源仍是 10-09 01:53 的旧快照，且同源优先 → 卡死。

**现在的实现**：`取全模块快照地址()` 直接返回 jsDelivr 目录，**单一数据源**。

```
后端地址 = "https://cdn.jsdelivr.net/gh/dqlvxy/astock-recs-bot@main"
today.json → <后端地址>/today.json
watch.json → <后端地址>/watch.json
recs.json  → <后端地址>/recs.json
```

**部署目录里不要放这三个 JSON**（已删除）。放了就是死文件，还会引发 SPA 回退误判。

### 8.20 十七次变更（2026-11-09 12:45）：处置 8.19 留下的两条风险

**老板指令**：修复遗留风险。

#### 风险一：推送失败静默丢产物 —— 已修

**现场**：两个 workflow 都是同一段坏逻辑

```bash
git pull --rebase --autostash origin main || true   # ← 失败被吞
git push origin main                                # ← 必然 non-fast-forward 被拒
```

`|| true` 把 pull 的错误吞掉，紧接着 push 因为落后被拒，整步以 `bash -e` 退出。后果：当次产物进不了仓库（artifact 里有，但看板当天不更新），日志只显示 "failed to push some refs"，看不出根因。

**改法**：逻辑抽成 `scripts/提交产物.sh`，两个 workflow 各改一行调用它。

```bash
for ROUND in 1..5:
  git fetch origin main          # 拿远端最新
  git rebase origin/main         # 落后则前移；冲突就 abort
  git push origin main           # 成功即跳出，被拒则重试
全失败 → ::error:: 注解（Actions 标红）+ exit 1
```

**为什么抽成脚本**：改 `.github/workflows/**` 需要 PAT 具备 `workflow` scope，缺了 GitHub **故意返回 404 而不是 403**（防探测），这次就卡在这里。抽出来后，以后调推送策略只改脚本，不再碰 workflow 文件。

**实测三种场景**（在 `/tmp` 建真实 git 仓库 + 裸远程模拟并发）：

| 场景 | 构造 | 结果 |
|---|---|---|
| 远端被抢先 | 甲先推 recs，乙基于旧基线推 params | 第 1 轮 rebase + push 成功，两边文件都在，历史**线性无 merge** |
| 同一行冲突 | 甲乙改 params 同一行 | 每轮 abort 干净，2 轮耗尽后 `::error::` + exit 1，工作区**残留 0 项** |
| 无改动 | 产物与云端一致 | `git diff --cached --quiet` → "文件无变化"，不产生空提交 |
